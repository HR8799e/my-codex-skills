# 自然数模代码

## 目标

把代码写成参赛队员为解决当前题目形成的工作脚本，而不是通用软件模板。优先级依次为：结果正确、思路易懂、代码从简、便于赛中修改。

不要通过随机改名、故意写乱、制造错误来模仿人。不要声称代码因此成为“人工编写”或能规避检测。自然感应来自代码结构与真实解题过程匹配。

## 默认结构

- 优先采用单文件、从上到下的顺序：导入库、读取数据、计算、绘图或输出。
- 固定任务中的少量重复可以保留。四条曲线可以直接写四次绘图语句，不要仅为消除重复建立配置表和循环。
- 只有数学步骤较长、逻辑确实重复或拆分后明显更易懂时才定义函数。
- 默认不要加入 `argparse`、`from __future__`、类型注解、数据类、日志系统、配置类、公共工具模块和多层路径封装。
- 不为一行操作创建只包装一行的函数。
- 数据文件固定时优先使用简单相对路径；只做当前任务真正需要的输入检查。

如果用户给出已有代码风格，先沿用其组织习惯和符号体系，再做必要改动。

## 命名

- 使用短而具有题目含义的名字，如 `x`、`t`、`v0`、`v100`、`r`、`theta`、`loss`、`ans`。
- 优先采用论文公式、题目符号和队员自然使用的缩写。
- 避免给局部简单变量使用完整句式般的长名字，如 `velocity_profile_at_100_seconds`。
- 避免泛化模板词堆叠，如 `current_series_configuration`、`output_figure_directory`。
- 不要为了显得自然而退化成难以辨认的随机字母。变量只需在当前局部范围内一眼可懂。

## 注释

把注释写成队员之间的定位标签或决策备注，不要写成面向陌生初学者的教程。

- 下一行已经完整表达含义时，删除注释。不要写“读取数据”“绘制曲线”“保存图片”这类复述操作的注释。
- 注释优先解释模型含义、公式来源、特殊约束、参数选择和不明显的科学表达决定。
- 使用简短中文片段，不追求完整、圆润、标准化的说明句。
- 局部决定放在行尾，例如 `plt.ylim(0.996, 1)  # 放大速度差异`。
- 一组计算需要定位时，在代码块上方写短标签，例如 `# 供货稳定指数`、`# 交叉和变异`。
- 简单绘图脚本可以没有注释或只有一两条关键注释；复杂模型才随算法阶段增加注释。
- 一次性脚本默认不写长篇文件说明和形式化函数文档字符串。

用户明确要求提交“无注释版”时，删除提交求解代码中的全部注释令牌，以及模块、函数和类的说明性文档字符串；保留必要空行，使计算阶段仍容易辨认。不要误删字符串数据、十六进制颜色值、输出文字或 README 内容，也不要连带清除内部论文生成工具中的维护注释。异常保护属于程序逻辑，不因去注释而删除。

避免这种教程式注释：

```python
# 设置纵轴范围，以便更加清晰地观察不同曲线之间的细微差异
```

优先写成：

```python
plt.ylim(0.996, 1)  # 放大速度差异
```

## 排版

- 严格保证语法、缩进和计算正确，但保持自然紧凑。
- 用少量空行按真实解题阶段分组，不为追求对称而机械分段。
- 普通函数调用能清楚放在一行时不要强制每个参数单独占一行；确实过长时再换行。
- 不要求所有相似语句拥有完全相同的视觉形状，但同一局部写法应容易阅读。
- 不故意加入不一致空格、错误缩进、废弃变量或无用语句。

## 绘图

- 将颜色、线型、图例等设置直接放在相应绘图语句附近。
- 保留坐标名称、单位、必要图例和影响解释的坐标范围；装饰只在论文表达需要时添加。
- 坐标截断、归一化或局部放大应在代码注释、图内说明或论文图注中至少说明一处。
- 输出应在论文尺寸下清楚；用户要求时同时保存高清位图和矢量图。

## 交付前检查

1. 运行代码，确认输出与题目数据和论文叙述一致；绘图任务还要实际查看图片。
2. 删除对当前任务没有实际作用的封装、验证、参数和注释。
3. 检查变量名是否能更短而不丢失题目含义。
4. 检查少量直接重复是否比配置表或通用函数更容易理解。
5. 确保精简没有牺牲公式正确性、可运行性、来源标注或科学严谨性。
